# Animated figures

Animated versions of Bioinformatics Algorithms figures, in the same visual
style as the static ones. Each animation is generated by a script in this
folder so it can be corrected and re-rendered rather than redrawn by hand.
Rendered output lives beside the static figures under `images/<Chapter>/`.

## Contents

| Animation | Output | Generator |
|---|---|---|
| Leo the ant builds an Eulerian cycle (Chapter 3, Assembly) | [`images/Assembly/Leo_eulerian_cycle.gif`](../images/Assembly/Leo_eulerian_cycle.gif) | `leo_eulerian_cycle.py` |

`make_gif.py` is the shared frame assembler.

## Leo the ant

The animated counterpart to `images/Assembly/Leo-1.png` through `Leo-6.png`.
It shows the Eulerian cycle being constructed in the three acts the stills
step through, so the reason the algorithm works is visible rather than
asserted:

1. **Green.** Leo starts at an arbitrary node and walks along unused edges
   until he gets stuck. He has used 4 of the 11 edges, and he is stuck at the
   node he started from, which is the whole insight: in a balanced graph you
   can only ever get stuck where you began.
2. **Blue.** Restart at a node on the cycle that still has an unused edge,
   re-walk the existing cycle from there (which renumbers it), then keep
   going along fresh edges. Stuck again, at 8 of 11.
3. **Red.** The same move once more, and this time every edge gets used.

A running "N of 11 edges used" counter, tinted the current act's color, makes
the progress readable without counting arrows.

### Regenerating

Requires Python 3 with `matplotlib`, `numpy`, and `Pillow`, plus the Optima
font (standard on macOS).

```
cd animations
python3 leo_eulerian_cycle.py ../images/Assembly/Leo_eulerian_cycle.gif
```

The script prints its structural checks, then the frame count and playback
length. Output is 800x600, about 50 seconds, and loops forever.

### Embedding

The repository is public, so the raw URL can be used directly in Cogniterra

## Method

Three things make these animations trustworthy and readable. They apply to any
new animation added here.

### 1. Derive the figure, never retype it

The graph was not transcribed by eye. Node centers and all 11 directed edges
were recovered from the source PowerPoint's connector shapes: node centers
from each oval's position and size, edge direction from each connector's
`flipH`/`flipV` flags combined with which end carries the arrowhead, then each
endpoint snapped to its nearest node center. Hand-typed structure is where
errors hide, and a beautiful animation of the wrong graph is still wrong.

Note that `soffice` skips hidden slides when converting a deck to PDF, so
PowerPoint slide numbers and PDF page numbers diverge. Map between them by
testing `slide.element.get("show") == "0"`.

### 2. Assert correctness in code, not by looking

The script refuses to render until the structure checks out. It verifies the
graph (7 nodes, 11 distinct edges, every node balanced so a cycle must exist,
all nodes reachable), then every act (each is a closed walk over real edges
with no repeats, each keeps all of the previous act's edges, each restart node
genuinely had an unused edge at that moment, and act 3 uses all 11 edges
exactly once and returns to its start). It also checks the drawing itself:
every edge stops just short of both endpoints, and no edge number overlaps
another edge, node, or number.

That last check exists because hand-tuned label offsets kept colliding in the
congested middle of this graph, where four edges cross. Label positions are
now chosen by a small solver that maximizes clearance, and then asserted.
Independent confirmation that the whole reconstruction is right: the final
frame matches the published `Leo-6.png` edge for edge and number for number.

### 3. Pace for a reader, not for the geometry

A uniform frame delay paces an animation by how much motion each step needs,
which has nothing to do with how long a person needs to understand it. A
caption that appears for a single frame is invisible no matter how good the
frame is. So playback time is budgeted in three separate ways:

- **Motion** runs at a steady 110 ms per frame.
- **Caption changes are timed events.** When the text changes, a still frame
  is held for roughly `500 ms + 42 ms per character` (clamped to about
  1.5 to 3.2 seconds). A caption the viewer has already read is discounted to
  60%. Each caption also covers a whole block of steps, so text never flips
  mid-motion.
- **Decision points get a beat.** Where the algorithm makes a choice, here the
  ant arriving at a node and having to pick an unused edge, the frame holds
  about 300 ms. Replaying already-known territory runs faster, about 130 ms.

Holds are nearly free in file size, because identical consecutive frames
collapse into a single frame with the summed delay. Being generous with
reading time costs playback length, not bytes. GIF stores delays in
centiseconds, so keep every duration a multiple of 10 ms or real playback
silently runs shorter than what the script reports.

The knobs are named constants at the top of the generator (`MOTION_MS`,
`READING_PER_CHAR_MS`, `NODE_ARRIVAL_MS`, `FRAMES_NEW_EDGE`), so pacing can
be retuned without touching any geometry.

## Style

These follow the same conventions as the static figures: Optima for prose and
labels, Courier bold for sequence text, dark grays rather than pure black,
the standard palette (blue `#176FC1`, green `#149B52`, red `#ED1C24`, purple
`#95319E`), shadowed gray nodes with no white ring, and edges that stop about
0.06 in short of the nodes they connect.
